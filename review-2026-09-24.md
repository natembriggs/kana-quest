# Review, 2026-09-24: bugs, usability, speed

A fresh pass over Kanji Trail (the app was called Kana Quest when the
earlier reviews were written). **This file is the current punch list.**
`review-followups.md` (to 2026-09-08) and `kanaquest-evaluation.md`
(2026-08-20) are kept as history. Their open items that still apply are
carried into the "Still open from earlier reviews" section below, so you
don't need to read them to know what's left.

Method: all test suites run (under Node on Linux, see below), a real
Chromium pass at 390×844 (boot, profile creation, onboarding, a simulated
update), and a read of the boot path, the service worker, the reader's
exit paths, profile persistence and the last day's commits. It was not a
line-by-line audit of `src/app.js`, which has 13,800 lines.

## Shipped in this pass

All in one commit, version `2026-09-24f`. All 9 suites pass under Node,
and `node test/build-story-art.mjs` passes. Not yet run under JSC: that
happens in the macOS CI job when this branch is merged.

1. **Offline boot after an update could fail.** `sw.js`'s `SHELL`
   precache list was missing three modules `src/app.js` imports at boot:
   `src/fsrs.js`, `src/vocab.js` and `src/data/vocab-manifest.js`. The
   `activate` handler deletes the previous version's cache. So after
   every release those three files were missing from the cache until the
   next online launch, and a learner who went offline in that window got
   an app that wouldn't start. They are now precached.
   `test/service-worker.js` now walks `app.js`'s real static-import graph
   (and `index.html`'s `<script src>`s) and fails if anything is missing
   from `SHELL`. I checked that the new test fails without the fix.
2. **An update no longer reloads the app mid-session.** Before, when a
   new service worker took control, `watchForUpdates()` reloaded
   straight away. `registration.update()` runs every time the app comes
   back to the front, and there are several releases a day. So a learner
   halfway through a quiz, a writing drill, a story or the feedback form
   lost that work and ended up on the profile picker. Now the reload
   waits until the learner is on the profile picker or the home screen
   with no sheet open. A reload from home reopens the same profile (via
   a one-shot `sessionStorage` key), so they end up where they were. I
   checked this in Chromium: an update event during onboarding did
   nothing, and skipping to home then reloaded back onto home.
   - Known trade-off: until that reload, the old page runs the old code
     under the new worker. So a data file loaded on demand
     (`kanji-grade-*.js`, a story) comes from the new release. That's the
     same exposure the old code already had in the moment before its
     reload. The data files have been backward-compatible so far. If
     that ever changes, version the data URLs.
3. **Markup in the profile emoji.** `renderProfiles()` was the only place
   that wrote `profile.emoji` via `innerHTML`. The emoji comes from a
   backup file or a sync, just as the name does, so it was a (low-risk,
   self-inflicted) HTML-injection path. It now uses `textContent`, like
   the other three places that render it.
4. **`vendor/wanakana.min.js` is now `defer`.** It used to be a
   render-blocking classic script in `<head>`, in front of ~100KB of
   markup and the splash. Deferred classic scripts and module scripts
   run in document order, so it still runs before `src/app.js`.
5. **The tests hid errors.** `closeDialog()` calls `removeEventListener`
   and `contains` on the sheet, and the stub DOM in `test/wiring.js` had
   neither. The resulting `TypeError` was thrown inside an `async` click
   handler. JavaScriptCore's shell drops unhandled rejections silently,
   so CI was green while `closeCompare()` threw on every run. The stubs
   are fixed.
6. **Tests now run under Node, and CI runs them there too.**
   `node test/run-node.mjs` runs every suite under Node, with the three
   JSC shell globals the suites use (`load`, `print`, `readFile`)
   provided. It works on Linux, in cloud sessions, and on a Mac without
   Xcode. Node also fails on an unhandled rejection, which is how item 5
   was found. `.github/workflows/test.yml` has a new `test-node` job
   (ubuntu) that also runs `test/build-story-art.mjs`, which CI never
   ran before. JSC is still the reference runner.

## Findings not yet acted on

Ordered by how much I'd expect each to matter to a learner. Effort: S =
under an hour, M = an afternoon, L = more than a day.

### Usability

**U1. ~~The system Back gesture closes the whole app (Android).~~ Done
2026-09-24.** The app never touched the History API (no `pushState`/
`popstate`), so in a standalone PWA on Android, Back or the edge-swipe left
the app outright, whether you were in a quiz, a story or Settings. `show()`
(`src/app.js`) now pushes a history entry for every screen except the three
hubs (`screen-profiles`, `screen-home`, `screen-onboarding`, where Back
leaving the app is correct) and replaces on those hubs, which collapses
however deep the stack got back to one entry — Back from a hub always exits
in one press regardless of path taken. A `popstate` handler routes to the
same place each screen's own on-screen back button goes: the ~10 back-style
`data-action` cases (`go-home`, `go-course`, `close-settings`, `detail-back`,
`reader-back`, `study-history-back`, `contributions-back`, `quit-session`,
`sweep-cancel`, `onboarding-back`) were factored into named `backFrom*`
functions, keyed by screen in `SCREEN_BACK_HANDLERS`, so the on-screen
buttons and the gesture share one implementation. An open sheet takes
priority, same as Escape (`closeTopmostSheet()`, extracted from the existing
Escape handler and extended to cover `reader-settings-sheet`, which Escape
had missed): Back closes just the sheet and restores the history entry the
gesture had to pop to get there, so the screen underneath still has one to
pop next time. `test/wiring.js` covers the hub collapse, the sheet-priority
restore, and that a second Back after a sheet closes genuinely leaves the
screen; verified live in Chromium too — mid-quiz Back now returns to the
course screen instead of closing the app, and closing a reader-settings
sheet via Back leaves the reader in place, with no console errors either
way. iOS standalone still has no Back gesture, so this was Android (and
desktop-browser) only, as scoped.

**U2. ~~Every launch starts at the profile picker. Medium, S. Owner
decision.~~ Shipped.** Owner chose the middle ground: a device with
exactly one profile now boots straight into it (`resolveBootProfile()` in
`src/app.js`, folded into the same one-shot decision as the update-resume
key it builds on). Zero profiles still opens the first-run create form;
two or more still shows the picker, and the in-app "switch profile"
action always shows the picker regardless of profile count, since that's
the only way to add a second one.

**U3. The contrast plan is still unbuilt. Medium, M.** `contrast-plan.md`
(2026-09-08) is still marked draft/not built. `--accent: #e8553d` and
`--tier-3: #5cb663` are unchanged in the light theme. The plan is fully
specified. It only needs building.

**U4. Leaving a story from the end card skips the reader's exit path.
Low, S.** The top-bar `reader-back` action flushes the bookmark,
disconnects both reader observers and closes the definition card. The
end card's "Back to stories" buttons (`reader-end-library`,
`reader-continue-library`) and the chapter-to-chapter `openStory()` calls
skip that. Nothing is lost today: the 800 ms bookmark timer still fires,
and `renderReaderBody()` re-creates the observers. But the paragraph
`IntersectionObserver` stays live on a hidden screen, and the reader now
has five exit paths with three different behaviours. Fold them into one
`leaveReader()` helper before the next reader feature adds a sixth.

### Speed

Measured sizes on the boot path: 1.39 MB of JavaScript in `app.js`'s
static import graph (≈450 KB gzipped, together with `styles.css` and
`index.html`), with `app.js` alone at 632 KB raw / 193 KB gzipped.

**S1. Every launch re-downloads the whole app. Done 2026-09-24, pending
a real-iPhone check.** `sw.js` now fetches with `cache: 'no-cache'` (a
shared `REVALIDATE` constant, which `test/service-worker.js` checks every
worker fetch uses). Measured in Chromium against `python3 -m
http.server`, per launch in a fresh tab: before, 32 full `200`
downloads; after, 34 bodiless `304`s and no full downloads. The first
visit went from 70 full downloads (page, then install, each downloading
everything) to 38. An edited file still came through fresh on the next
launch, and offline boot still works. **Still to do by hand:** on the
home-screen app on an iPhone, deploy, edit a file, relaunch, and confirm
the edit shows. If Safari ever serves a stale file, revert the one
constant. The original finding: `sw.js` fetches everything with `cache: 'no-store'`,
which skips the HTTP cache completely. No `If-None-Match` is ever sent,
so the server can never answer 304, and every launch downloads all
~450 KB gzipped again. The launch also waits on the network the whole
time, because the fallback to cache only happens when the network fails,
not when it is slow. `cache: 'no-cache'` keeps the property the comment
in `sw.js` wants (always revalidate, never trust heuristic freshness) but
lets unchanged files come back as a 304 with no body. Both GitHub Pages
and Cloudflare send ETags. This is small, but it changes a deliberate
decision made around iOS staleness, so check it on the real home-screen
app on an iPhone before shipping: deploy, edit a file, relaunch, and
confirm the edit shows.

**S2. The runtime cache is wiped on every release. Medium, M.** Every
release deletes the entire `kana-quest-<VERSION>` cache. That includes
the kanji grade data, stroke data, stories and story paintings cached
on demand. With several releases a day, "previously viewed paintings
work offline" (a `test/service-worker.js` check) only holds until the
next deploy, and each story and kanji grade gets downloaded again after
every update. The paintings already have content-hashed URLs (`?v=<16
hex>`). Move them into a separate cache that isn't tied to the release
version (e.g. `kana-quest-art`), and trim it by keeping only URLs still
referenced by the current story manifest, not by deleting the whole
cache. `src/data/*` could get the same treatment once it has
content-versioned URLs.

**S3. Every response waits for its own cache write. Low, S.** The fetch
handler awaits `cache.put()` before returning each response, so a 680 KB
story file isn't handed to the page until the copy in Cache Storage has
been written. The usual pattern is to return `fresh` straight away and
keep the worker alive with `event.waitUntil(cache.put(...))`. A test
currently asserts the await ("a successful fetch waits for its runtime
cache write"), so this was a decision. Worth revisiting alongside S1.

**S4. Boot-time JavaScript. Done 2026-09-24, in part.** Five modules
left `app.js`'s static import graph and now load with `import()` the
first time they're needed: `src/changelog.js` (opening Settings),
`src/feedback.js` (the feedback sheet, or checking on a report you sent),
`src/sync-protocol.js` + `src/sync-transport.js` (only once a profile is
paired) and `src/reader.js` (opening a story, alongside the story's own
data). Each has one cached loader, and the async call sites keep the
existing `navSeq` guard. The one race this created was also fixed:
`reopenDraft()` used to write `state.feedbackDraft` right after
`openFeedback()`, which a slow first load could then overwrite. Now it
passes the draft in. All five stay in `SHELL`, so their screens still
work offline.

The 22 modules still on the static graph get a `<link rel="modulepreload">`
in `index.html`, so the browser fetches them in parallel with `app.js`
instead of discovering them one level at a time. `test/service-worker.js`
checks both ways that that list matches the static graph. It also checks
that `SHELL` covers the static graph plus every app-code module reached
through a plain `import('./x.js')`. Per-grade and per-story data under
`src/data/` is excluded, as before.

| boot graph | modules | raw | gzip |
|---|---|---|---|
| before | 28 | 1,394,706 B | 449,543 B |
| after | 23 | 1,265,407 B | 402,543 B |
| change | −5 | −9.3% | −10.5% |

In Chromium, none of the five was fetched at boot, and each was fetched
once, when its screen opened. Boot, Settings, feedback, a writing session
and a story all worked with no console errors, and so did the same flow
offline after one online visit.

Looked at, and left for a separate pass:
- **`src/data/vocab-manifest.js` (202 KB, the biggest file at boot).**
  `src/vocab.js` builds `VOCAB_COURSES` from it at module load, and the
  home screen's synchronous `courseStats()` reads that. Making it lazy
  needs either an async course list or a second, smaller generated
  manifest. That's a refactor, not an `import()` swap.
- **Writing mode (`writing.js`, `stroke-grader.js`, `stroke-geometry.js`,
  33 KB).** It's called from a dozen synchronous sites, including the
  pointer handlers that draw ink, and Settings reads
  `STRICTNESS_LEVELS` too. It's doable with one await where a writing
  session starts, but it needs its own careful pass.
- **`src/contributions.js` (20 KB).** It runs right after every home
  render (`catchUpOnContributions()`), so lazy loading would only move
  the fetch a moment later.

**S5. Every graded answer rewrites the whole profile. Measured
2026-09-24: not needed yet.** The owner's backup file is 752 KB, under
the ~1 MB threshold below. Re-measure if it grows past that. The
original finding: `store.saveProfile()` `put`s the entire profile document on
every answer (58 call sites). It then opens up to two more transactions
to set the sync dirty flag. `store.js`'s header comment still says
"profiles are small (a few hundred records each)". With 2,136 jōyō kanji
× several modes plus vocab, a long-term learner's profile is much
bigger than that. Export your own profile from Settings and check its
size. Over ~1 MB, this is worth fixing, by batching writes (debounce like
the reader bookmark already does, and flush on `visibilitychange`) or by
moving progress records into their own object store.

**S6. `app.js` is 13,800 lines.** `review-followups.md` decided against
splitting it "at its current size", but it has grown a lot since. After
S4 it's most of what's left on the boot path (632 KB raw, 193 KB
gzipped). The Stories reader section (`openStory()` through the reader's
definition card and settings handlers, roughly lines 12,100 to 14,000)
is the best next candidate. It's reachable only through `openStory()`,
and its state all sits under a `reader*` prefix, so it can be extracted
into its own lazy module behind the same await S4 added there. The work
is mostly confirming that nothing outside that section reaches into it.

### Bugs to keep an eye on

- **Tests only run under JSC locally.** Fixed as far as CI goes (item 6
  above). It's still worth running `node test/run-node.mjs` before
  pushing: it catches a class of error that JSC hides.
- **A mixed-version window after an update** (item 2's trade-off). No
  action needed now. Just don't make a breaking change to the shape of a
  lazily loaded data file without changing its URL.
